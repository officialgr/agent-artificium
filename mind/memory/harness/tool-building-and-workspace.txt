Purpose

Tools are reusable apparatus that extend or interface with Artificium.
Executable tools belong below `mind/tools/`. Ordinary projects, experiments,
websites, manuscripts, datasets, and collaborative work belong below
`mind/space/`. Reusable knowledge about a tool belongs in `mind/memory/tools/`;
general lessons learned while building it belong in the appropriate semantic
memory branch.

Tool-building strategy

- Build a tool when repeated, exact, asynchronous, external, or computational
  work is better expressed as tested code than repeated reasoning. Do not create
  wrappers that add no capability or reliability.
- Define the smallest useful interface. Keep identifiers, paths, timestamps,
  outputs, and errors explicit enough for future debugging.
- Test the real boundary: network failure, malformed input, restart, duplicate
  events, large output, or concurrency when relevant. Never treat code creation
  alone as proof that the tool works.
- Put large outputs and mechanical state in appropriate workspace or logs, not
  semantic memory. Preserve only invocation, verified behavior, limitations,
  failure lessons, and retrieval triggers in memory.
- Give the executable and its memory descriptive names. Update the existing tool
  memory when behavior changes.
- Maintain the **Available tools and apparatus** section of `meta_memory.md` when
  an important tool is created, adopted, changed, or removed. Record its path,
  verified purpose, when to use it, and the route to deeper operating memory.
  Keep major tools directly visible and use `memory/tools/index.txt` plus deeper
  semantic indexes when the registry grows.

Reference example

`mind/tools/scheduler.py` is an editable executable tool loaded by the harness
at runtime startup. It stores mechanical task state under logs, waits without
model calls, and emits due work through the ordinary interaction boundary. Its
operating guide is `memory/tools/scheduled-actions-through-interactions.txt`.
This demonstrates a useful pattern: combine a small deterministic tool with an
existing Artificium capability instead of adding a second agent architecture.
It is also the seed entry in meta-memory's tool registry; new verified tools
should extend that registry rather than remain discoverable only by accident.

General-harness reasoning

Before concluding that a capability is missing, reason from the primitives:
interactions carry entity-neutral events and attachments; Linux and files build
apparatus; the scheduler emits future interactions; Infinite Attention reads
large evidence; memory preserves learned operation. For example, a new
conversation needs only a new interaction ID, a screen companion is an
authorized capture tool plus image interactions, and another Artificium is just
another entity producing events. Build a specialized tool only for mechanics
that the composition actually lacks.

Other combinations

- A chat UI is a reusable interaction client and belongs in `mind/tools/`; a
  website being built for an entity belongs in `mind/space/`.
- A screen observer can capture authorized images and write interaction events;
  Artificium can load relevant images, build OCR fallback, and form memory from
  repeated work patterns.
- A search tool can return bounded structured results while Infinite Attention
  processes large fetched corpora and memory records validated research habits.
- A tool can schedule its own later verification by emitting or requesting a
  scheduled interaction rather than keeping the life-loop busy.

Client contract

Before building a chat UI, screen observer, sensor, or agent bridge, inspect
`artificium-code/REFERENCE.md`. Prove the durable event boundary first:
thread discovery, atomic inbound writes, notification reconciliation, outbound
polling, exact sender/recipient/reply IDs, and attachments. Only then add visual
design, Markdown sanitization, uploads, authentication, or convenience
features. Consult `README.md` for the current process commands; a client being
open does not imply that the life-loop is stopped when the client exits.

Update this guide when tool-building experience establishes better placement,
interfaces, testing, observability, or integration patterns.
